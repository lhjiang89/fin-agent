## 二、调用链

```text
用户问题与 as-of
    ↓
CLI 检查是否明确指定腾讯
    ↓
DeepSeek 收到消息和工具 schema
    ↓
assistant 返回 tool_calls：名称、参数、id
    ↓
程序校验名称和参数，并注入 cutoff
    ↓
工具读取缓存，必要时查询 Futu OpenD
    ↓
tool 消息带 tool_call_id 返回结果
    ↓
DeepSeek 继续调用工具或生成回答
    ↓
保存运行状态、消息轨迹与耗时
```

模型提出调用意图，应用程序负责执行工具和约束数据范围。一次 assistant 消息可以包含多个 `tool_calls`；当前实现逐个执行。

## 四、手写循环与 LangGraph

手写版用 `while` 和局部变量维护消息与计数。LangGraph 版用 `AgentState`、`model` / `tools` 节点和条件边表达同一流程。两者共用工具 schema 和执行器，截止日期由程序传入。

假模型对照脚本中两者都完成一次工具调用。图测试在双工具场景比较完整 `RunResult`。这不代表全部故障路径完全一致。当前 LangGraph 没有配置 checkpointer，也没有实现重启恢复。详细说明见 [Day 14 对照](../DAY14_COMPARISON.md)。

## 五、面试题与参考答案

### 1. 从用户提问到工具执行，每一步由谁负责？

服务端把问题、上下文和工具 schema 发给模型。模型返回调用意图，包括工具名、参数和调用 ID。应用校验名称和参数，注入可信的截止日期，再调用行情或公告函数。结果作为 `role: tool` 消息回传，并通过 `tool_call_id` 关联原调用。模型随后继续调用或给出回答，应用控制最大次数和总时间。

### 2. Function Calling 的核心原理是什么？

模型根据工具描述生成结构化调用请求。SDK 或业务程序解析请求，校验参数，调用实际函数，再把执行结果发送给模型。工具 schema 帮助模型构造参数，但服务端仍需独立验证。

### 3. 为什么 `tool_call_id` 很重要？

一次模型响应可能包含多个工具调用。ID 让每条工具结果对应到正确的调用，也让日志能够把请求、执行和结果串起来。Fin-Agent 的真实 trace 有两个调用，各自对应一条 tool 消息。

### 4. 模型反复选错工具或参数非法，怎么办？

未知工具、非法 JSON、字段错误或不允许的标的应在执行前拦截。可以把结构化错误作为工具结果回传，让模型修正或澄清；程序不应自动重复同一组非法参数。同时设置最大工具调用次数和总时间，避免无限循环。

### 5. 工具超时或连接失败时，如何处理？

对于确认属于暂时故障的只读查询，可以在总预算内有限重试，记录调用 ID、错误类型和尝试次数。超时或重试耗尽后返回明确失败状态。当前项目只对 `ConnectionError` 和 `OSError` 做有限重试，Futu `RuntimeError` 尚未分类；等待超时也不能强制停止已运行线程。

### 6. 为什么截止日期由应用注入？

历史研究只能使用截止时点可见的信息。Fin-Agent 的模型参数 schema 不包含 `as_of`，额外字段会被拒绝；执行器从用户请求取得截止日期并传入工具。这比仅在提示词中要求模型遵守日期更可验证。当前公告仅有日期精度，不能据此严格判断当日盘前与盘后。

### 7. 如何防止 Agent 反复调用同一个工具？

设置工具调用次数上限和总超时，达到上限后明确返回未完成。测试中，假模型一直请求成功的行情工具，`max_steps=2` 时只执行两次并以 `max_steps` 结束。更复杂的重复检测可以作为后续优化，需避免拦截参数变化后确有意义的查询。

### 8. 手写 Agent 和 LangGraph 有什么区别？

手写版显式维护循环、消息和计数，适合解释底层流程。LangGraph 版用共享状态、节点和条件边表达流程，更容易看出分支；当前两者仍自行实现工具执行与错误处理。本项目的图没有启用检查点，不能宣称已经具备持久化恢复。

### 9. 框架有检查点就能保证交易不重复吗？

不能直接得出这个结论。检查点用于保存流程状态，外部交易可能已经成功但状态尚未记录。写操作需要业务幂等键、可靠的订单状态查询、事务和对账。当前项目只有只读研究工具，还没有完成交易闭环。

### 10. 如何判断 Agent 真正完成了任务？

`completed` 表示模型返回最终文本，还要检查引用是否支持结论、数据是否覆盖请求时点、公告搜索是否完整以及用户问题是否得到回答。后续应建立固定题集，分别评估最终结果和工具轨迹，记录分母、失败类型、延迟和成本。

### 11. 行情缓存会带来什么问题？

本项目曾因为只检查截止日前是否存在记录，把 2025 年行情用于 2026 年问题。现在没有截止日记录时会回源，当天也会重新查询。但休市日会重复回源，且尚未用交易日历和数据时点完整判定日线是否为最终收盘。缓存合并和复权版本管理也需要进一步设计。

### 12. Futu 公告搜索能代表完整公告库吗？

不能。当前通过关键词和 `NOTICE` 类型搜索，再按关联证券筛选；接口返回有限搜索结果，发布时间目前只有日期精度。没有查到公告不等于不存在，也无法精确比较当天盘前和盘后。应让回答披露这些限制。

## 六、90 秒项目介绍

我在 Fin-Agent 中实现了股票研究的工具调用循环。用户提交腾讯行情或公告问题后，DeepSeek 根据工具 schema 返回工具调用，应用校验参数并注入截止日期，然后通过本地缓存或 Futu OpenD 获取数据。工具结果通过调用 ID 回传模型，模型可以继续调用或生成回答。系统设置调用次数上限、总超时和连接故障的有限重试，并保存每次运行轨迹。我还用 LangGraph 的状态、节点和条件边实现了一个对照版本，复用相同工具和参数边界。在一次真实轨迹中，模型在同一条消息里提出行情和公告两个调用，两个结果分别通过 ID 回填。当前项目仍是只读研究原型，公告搜索完整性、精确发布时间、缓存覆盖和任务恢复需要继续完善。

# Fin-Agent 第一周产出

## 一、项目目标

第一周完成一个最小可验证的股票研究 Agent。它连接本地 Futu OpenD 获取腾讯港股 `HK.00700` 的真实日线数据，使用 `--as-of` 控制可见数据范围，调用 DeepSeek 生成结构化回答，再由程序校验引用和复算涨跌幅。

第一周的重点是建立 Agent 的数据边界、模型调用、结构化输出和程序校验能力。

## 二、已完成的功能

### 1. 运行入口

项目支持以下 CLI 参数：

```sh
python -m fin_agent \
  --live \
  --symbol HK.00700 \
  --as-of 2025-11-19 \
  --question "最近两个交易日涨跌幅是多少？"
```

主要参数如下：

| 参数 | 作用 |
|---|---|
| `--symbol` | 股票代码，默认 `HK.00700` |
| `--as-of` | 数据截止日期 |
| `--question` | 用户的研究问题 |
| `--data` | 标准化行情 JSON 文件 |
| `--live` | 调用 DeepSeek |

### 2. Futu OpenD 数据接入

通过 Python SDK 连接本地 OpenD：

```python
OpenQuoteContext(host="127.0.0.1", port=11111)
```

使用历史日线接口获取数据，并将结果保存为：

- `fixtures/tencent_daily.raw.json`
- `fixtures/tencent_daily.json`

统一后的行情结构包含：

```json
{
  "symbol": "HK.00700",
  "market": "HK",
  "period": "1d",
  "date": "2025-11-19",
  "open": 621.2,
  "high": 625.2,
  "low": 610.2,
  "close": 615.7,
  "volume": 14015988,
  "source": "futu-opend"
}
```

### 3. 截止日期控制

`--as-of` 用于定义 Agent 在某个历史时点可以看到的数据。

```text
读取所有行情
    ↓
按 symbol 过滤
    ↓
按 date <= as-of 过滤
    ↓
将可见行情交给模型
```

如果用户传入的截止日期晚于本地行情最新日期，系统不会使用旧行情生成误导性结论，而是返回：

```json
{
  "conclusion": "无法基于当前行情数据回答该截止日期的问题",
  "change_percent": null,
  "citations": [],
  "missing_information": [
    "请求截止日早于本地行情最新日期"
  ]
}
```

### 4. DeepSeek 结构化输出

默认使用 `deepseek-flash`，通过 OpenAI 兼容接口发送请求。API key 从 `DEEPSEEK_API_KEY` 读取。

回答契约如下：

```python
class StockAnswer(BaseModel):
    conclusion: str
    change_percent: Optional[float] = None
    citations: list[str]
    as_of: str
    missing_information: list[str]
```

模型请求启用了 JSON Output，并且关闭了思考模式，以便在低输出 token 预算下稳定完成结构化回答。

### 5. 程序级校验

模型输出后，程序会检查：

- JSON 是否可以解析
- 字段类型是否正确
- 引用日期是否属于可见行情
- 是否有至少两条行情才能计算涨跌幅
- 截止日期是否超过数据覆盖范围
- 涨跌幅是否能由程序独立复算

模型负责生成结论和解释，程序负责事实边界和业务计算。

### 6. 调用记录

每次成功调用会写入 `runs/last_run.json`，例如：

```json
{
  "model": "deepseek-flash",
  "prompt_version": "day5-v1",
  "symbol": "HK.00700",
  "as_of": "2025-11-19",
  "visible_bars": 4,
  "elapsed_ms": 1829.24,
  "citations": [
    "2025-11-18",
    "2025-11-19"
  ]
}
```

每次发送给 DeepSeek 的请求 payload 也会打印到 stderr，便于检查模型实际收到的内容。API key 不会进入 payload。

## 三、真实运行结果

一次真实调用得到：

```json
{
  "conclusion": "最近两个交易日收盘价由 618.2 降至 617.2，涨跌幅约为 -0.16%。",
  "change_percent": -0.16,
  "citations": [
    "2025-11-18",
    "2025-11-19"
  ],
  "as_of": "2025-11-19",
  "missing_information": []
}
```

程序独立复算结果：

```text
-0.16176%
```

模型结果和程序复算结果一致。

## 四、第一周遇到的故障

### 故障一：模型返回空内容

初次调用时，DeepSeek 默认启用了思考模式，`max_tokens=500` 被思考过程消耗，最终返回空内容，并且 `finish_reason=length`。

修复方式：

- 通过请求扩展参数关闭思考模式
- 检查空响应
- 抛出包含 `finish_reason` 的错误

### 故障二：字段类型不符合契约

模型把 `missing_information` 返回成了字符串，而契约要求列表。

修复方式：

- 用 Pydantic 重新校验模型输出
- 对字符串形式做兼容归一化
- 在提示词中明确“没有缺失信息时必须返回空数组”

### 故障三：截止日期超过数据覆盖范围

当用户要求的截止日期晚于本地行情最新日期时，模型仍可能根据最后几条旧数据生成结论。

修复方式：

- 程序比较请求截止日期和行情最新日期
- 数据覆盖不足时不再接受模型结论
- 将 `change_percent` 设为 `null`
- 清空旧行情引用
- 返回明确的数据缺口

## 五、第一周掌握的核心知识

### Agent 基础链路

```text
用户问题
  ↓
数据加载
  ↓
数据过滤
  ↓
上下文构造
  ↓
模型调用
  ↓
结构化解析
  ↓
业务校验
  ↓
最终回答
```

### LLM 和 Agent 的区别

单次 LLM 调用只负责根据输入生成文本。Agent 应用还需要处理数据、工具、状态、校验、错误和执行结果。第一周虽然还没有实现多轮工具调用，但已经搭建了 Agent 的最小运行闭环。

### 模型和程序的职责边界

模型适合完成：

- 理解用户问题
- 组织语言
- 生成结论草稿
- 输出引用和缺失信息

程序必须负责：

- 时间范围过滤
- 权限和数据边界
- 数值计算
- 引用存在性
- 数据新鲜度
- 失败和重试策略

## 六、对应面试题与参考答案

### 题目 1：LLM 和 Agent 有什么区别？

参考答案：

LLM 主要负责根据上下文生成下一段内容。Agent 是围绕模型构建的运行系统，除了模型本身，还包括任务理解、工具调用、状态管理、记忆、结果校验和错误处理。我的 Fin-Agent 第一周实现了一个最小闭环，先从 Futu OpenD 获取行情，再按截止日期过滤数据，让 DeepSeek 生成结构化回答，最后由程序校验引用并复算涨跌幅。

### 题目 2：模型返回合法 JSON，为什么还可能是错误答案？

参考答案：

JSON 合法只说明格式符合要求，不代表事实正确。模型可能引用未来日期、使用不存在的行情、把字符串当数字，或者在数据不足时仍然给出结论。Fin-Agent 对引用日期、截止日期、数据完整性和涨跌幅分别做确定性校验。模型输出必须同时满足格式约束和业务约束。

### 题目 3：`--as-of` 是做什么的？

参考答案：

`--as-of` 定义 Agent 在指定历史时点可以看到的数据。程序只向模型提供 `date <= as-of` 的行情，从而防止未来数据泄漏。在历史回放、金融研究和策略评估中，必须把报告时间、公开时间、决策时间和成交时间区分开。`--as-of` 本质上是数据可见性的边界。

### 题目 4：如果请求截止日期晚于数据最新日期，系统应该怎么做？

参考答案：

系统首先比较请求截止日期和数据最新日期。如果数据没有覆盖请求时点，就不能把最后一条旧数据当成请求时点的数据。我的实现会返回数据覆盖不足，设置 `change_percent` 为 `null`，清空旧数据引用，并要求补充数据或修改截止日期。

### 题目 5：如何防止模型幻觉？

参考答案：

我会从数据、提示词和程序校验三层处理。数据层只提供经过截止时间过滤的真实行情。提示词要求只使用提供的数据，并且引用具体日期。程序层验证引用是否属于可见数据，并独立计算涨跌幅。模型的自然语言结论不能替代程序校验。

### 题目 6：为什么需要结构化输出？

参考答案：

自然语言结果难以稳定解析，也难以做自动评测。结构化输出可以让系统明确区分结论、数值、引用、截止时间和缺失信息。我的实现使用 JSON Output 加 Pydantic 模型校验，但结构化输出只解决格式问题，仍然需要业务规则检查。

### 题目 7：模型输出不符合 schema 时怎么办？

参考答案：

先记录原始响应和结束原因，再做有限的格式归一化。可以修复明确的类型差异，例如把单个字符串转换成列表。对于字段缺失、引用非法或数值不一致，应该拒绝结果并触发重试、澄清或人工处理，不能无限重试。

### 题目 8：哪些逻辑必须放在程序中？

参考答案：

时间过滤、权限判断、金额和涨跌幅计算、引用存在性、幂等和订单状态都必须由程序控制。这些逻辑具有确定性和业务约束，交给模型会产生不可重复的结果。模型可以提出建议或生成解释，但不能成为金融数据和交易状态的唯一事实来源。

### 题目 9：如何评估一次 Agent 调用？

参考答案：

至少要同时看任务结果和执行轨迹。结果层检查涨跌幅是否正确、引用是否支持结论、截止日期是否满足要求。轨迹层记录模型、提示词版本、输入数据版本、可见数据量、耗时、错误和引用。我的第一周已经保存 `runs/last_run.json`，后续可以在固定题集上比较成功率、延迟、成本和失败类型。

### 题目 10：你第一周遇到过什么问题？

参考答案：

第一次调用因为思考模式消耗了输出预算，返回空内容。修复后模型又把列表字段返回成字符串。最后我增加了空响应检查、结束原因记录、类型归一化和 Pydantic 校验。这个过程说明 Agent 调试不能只看最终文本，还要检查请求参数、响应状态、结束原因和 schema 校验结果。

### 题目 11：为什么不直接让模型计算涨跌幅？

参考答案：

模型可以先给出涨跌幅草稿，但最终结果必须由程序根据收盘价复算。金融数值计算是确定性逻辑，程序计算可以避免算术错误，并能在模型结果和真实计算不一致时拒绝回答或触发复核。

### 题目 12：第一周的系统还算完整 Agent 吗？

参考答案：

它是一个最小 Agent 应用闭环，还没有进入多工具自主规划阶段。第一周先完成了真实数据接入、时间边界、模型调用、结构化输出和程序校验。第二周会增加行情和公告两个只读工具，再实现模型选择工具、参数校验、工具执行、结果回填和有界循环。

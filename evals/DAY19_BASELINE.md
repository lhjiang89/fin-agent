# Day 19：固定工作流与工具循环基线

## 实验设置

- 评测集：Day 16 的 10 道开发题（D16-01 至 D16-10）。
- 模型：DeepSeek `deepseek-flash`，temperature 0；两组使用相同提示要求和 JSON 输出字段。
- 数据：冻结的 `evals/fixtures/day15_prices.json` 与 `fixtures/filings.json`，不连接 Futu OpenD。
- 固定工作流：程序每题按固定顺序读取行情、公告，再单次请求模型作答。
- 工具循环：沿用第二周手写工具循环，由模型选择工具；工具执行被适配到同一冻结数据，不触发实时回源。
- 重复次数：每题每种方法 1 次，共 20 道运行。以下是一次观察，不是稳定性或统计显著性结论。

## 一次实测

| 指标 | 固定工作流 | 工具循环 |
|---|---:|---:|
| 评分通过 | 10/10 | 10/10 |
| 动作、数值、引用、截止日期、缺失信息通过率 | 各 100% | 各 100% |
| 无法回答（模型标记数据不足） | 4/10 | 4/10 |
| 模型请求数 | 10 | 19 |
| 模型工具调用数 | 0（应用固定读取 20 次数据源） | 9 |
| 输入 token | 68,932 | 19,270 |
| 输出 token | 512 | 911 |
| 总 token | 69,444 | 20,181 |
| 10 题合计耗时 | 12.81 秒 | 19.81 秒 |

固定工作流在这组数据上用时较少，且答案均通过；但它每次都把完整公告缓存一并发给模型，因此 token 明显更多。工具循环没有按固定顺序读取无关数据，token 更少；多轮模型请求使总耗时更长。当前数据规模、单次重复和模型波动不足以证明某种架构普遍更优。

两种方案均对 4 道数据不足题正确表达了无法回答。D16-03 的“拒绝未来数据”归入拒绝动作而非“无法回答”计数。脚本把输出中常见的嵌套收盘价、公告缺失字段同义表述归一后计分；评分口径的版本也保存在 JSON 报告中。

## 面试复盘

**固定工作流和 Agent 循环如何取舍？** 固定流程节点少、可预测、延迟低，适合任务步骤稳定且都需要同一批数据的场景。Agent 循环可以按问题选择工具，避免无关读取，但需要多轮模型请求，延迟和控制复杂度上升。应在同一模型、数据、题目和预算下比较任务成功率、token、延迟及失败轨迹，再按产品约束选择；本次小样本只说明在该题集上的观察。
